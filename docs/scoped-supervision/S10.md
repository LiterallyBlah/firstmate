# S10: Resources, occurrences and scoped maintenance

Disabled implementation for independent R10 review, based on landed S08 and S09 (`3f74bb64`, PRs #154 and #157).
It installs nothing, registers no RPC, hook, timer or route, activates no job or scope, deletes nothing, sends nothing
and wakes nobody. `SupervisionResources` and `SupervisionJobs` refuse every entry point with `UNSUPPORTED` unless
constructed with `enabled: true`, which only tests do. No maintenance executor ships: an advisory host pass also
refuses `UNSUPPORTED` without one, because actual shared effects need receiver qualification (S11).

D5 is answered **option 1, durable daily occurrences** (`data/fm-ss-d5`): job/zone/date identity, one missed-day
catch-up observation, and resuming an unfinished host pass without duplicate effects. That contract is implemented
and tested here. Retaining daemon-local/no-catch-up semantics is the unselected alternative and is not claimed.

## What it adds

`shared/supervision-maintenance.ts` (schemas, the resource-key families, compatibility and the pure
`maintenanceSummary`), `server/supervision-maintenance-state.ts` (append/replay row checks and deterministic IDs),
`server/supervision-resources.ts` (arbitration), `server/supervision-jobs.ts` (the D5 scheduler, host passes,
incidents, cleanup planning and the timer inventory) and `templates/messages/maintenance-incident.md`. Five journal
row kinds join the S01 store the way S08's and S09's did: one schema union entry each, one change/row validator pair
in `SupervisionStore.apply`, and an optional `maintenance` status projection.

| Record | Identity | What the store enforces at append **and** replay |
|---|---|---|
| `resource-reservation` | an effect's ID, or a host pass and its pass number | Sorted keys taken all at once. Holders of one key are all shared (build/read) or one exclusive (cleanup/deploy/migrate). Each key's fence is issued once and is always the next. Expiry moves `granted → suspect`, never to released. Release needs terminal evidence matching the holder: an effect's `succeeded`/`failed` state, `withdrawn` only once it is `cancelled` (a `reserved` effect is still dispatchable by S04), or proof of non-admission of an *uncertain* effect recorded by the captain/mate with evidence; a host pass's finished state with every item settled, or `withdrawn` only for a pass that is not running and never dispatched anything. Holder, class, keys, priority and queue position are fixed |
| `maintenance-job` | job ID, under a registered `maintenance` scope | A schedule, coverage, resource or selector change takes the next definition version; nothing else does. Spend and first activation are retained. An advisory job cannot be active beside a legacy timer unless that timer is recorded `retired` with evidence (no duplicate cleaner) |
| `occurrence` | digest of job, IANA zone and local date | Opens with every covered host's pass; closes only when every pass is finished. Identity, coverage and the missed-day observation are fixed. Two occurrences of one job are never closer than 12 hours, so a zone change or DST shift cannot run one day twice |
| `occurrence-host` | digest of occurrence and host | One running pass per job and host. The item ledger is write-ahead and append-only: an item is `dispatched` before it is applied, never redispatched or forgotten, and is never left dispatched outside a running pass (it becomes `uncertain`). A pass with unsettled items cannot complete, fail or be superseded. Passes are counted once each and capped by the job's `maxPasses` |
| `maintenance-incident` | digest of job, host, kind and ordinal | One open incident per job, host and kind. Only a changed signature is a new generation. A resolved incident is final (its last wake may still be acknowledged) |

## D5 semantics (`planTick`, `dueInstant`)

- **Identity.** `(job, IANA zone, local date)`. The definition version is recorded on the occurrence, not keyed, so
  redefining a job mid-day never opens a second occurrence for that day. An unknown zone is refused by the schema,
  never read as UTC or daemon-local.
- **Due instant.** `HH:MM` in the job's zone via the runtime's Intl tz data. A wall time DST repeats runs at its first
  instant; one DST skips is read with the offset before the gap (02:30 in a one-hour spring gap runs at 03:30).
- **Duplicate tick.** The open command's request ID is derived from the occurrence ID. A second tick, or a second
  process ticking at the same moment, replays the same command and writes nothing.
- **Restart across due time / missed days.** A tick after the due time opens one occurrence for the latest due date,
  `trigger: "catch-up"` when more than five minutes late. Earlier due dates since the previous occurrence (and never
  before first activation) are listed once in that occurrence's `missed` observation (latest 31 dates, total count).
  They are never run separately.
- **Per-host resume.** A new occurrence supersedes the previous one's passes that have nothing in flight
  (pending/deferred/offline with no unsettled items, or left `running` by a crash with nothing dispatched and not run
  by this process), and releases what they held: a stranded pass is never run late as a second run that day. A pass with unsettled items stays open, keeps its reservation and
  blocks that host's newer pass. A pass found `running` by a process that holds no run for it was interrupted: its
  dispatched items become `uncertain`, never reapplied. Uncertain items hold the host until the captain/mate records
  receiver evidence (`reconcileItems`); then the pass resumes and applies only items never dispatched.
- **One offline host never stops the others.** Each host is probed independently. An offline host keeps coverage
  (`offline`, counted in the summary) and one `offline` incident; while it stays offline, each further drive writes
  nothing.

## Completion criteria

- **One accounted occurrence per host/date.** Occurrence identity, the 12-hour spacing row check, the derived open
  command ID and per-host rows written in the same transaction as the occurrence.
- **Unknown effects retain resources.** An uncertain/accepted/dispatching effect's reservation cannot be released
  except by recorded proof of non-admission; a host pass's reservation stays while any item is dispatched or uncertain.
  Expiry only marks a holder suspect, and a waiting request (even at higher priority) is not granted meanwhile.
- **Offline coverage honest.** Every covered host has a row; `maintenanceSummary` counts `offline`, `deferred` and
  `uncovered` hosts and reads as a lower bound when the journal is not current. The timer inventory is
  `complete: false` without a native schedule listing, and lists no native rows rather than claiming none exist.
- **No repeated healthy global wakeups.** Healthy passes and resolutions add no wake. An unchanged failure or outage
  writes no incident row. A new incident generation is one wake for the **maintenance scope** (`notify.pending`),
  counted against the job's turn budget; General is never a recipient and reads `maintenanceSummary` on demand. An
  unknown (`null`) or spent budget holds the wake (`held-budget`) and opens one `budget` incident.

## Resource arbitration (`SupervisionResources`, `grantable`)

All keys or none, in sorted order. Default FIFO within priority (1 first): a request waits behind any earlier
incompatible waiter on any of its keys, so a later build cannot starve a queued prune; compatible builds on unrelated
keys never wait. Starvation is exposed (`maintenanceSummary().resources.starving`, queued 32+ transactions); actual
cross-project priority disputes stay S09 `priority` conflicts. Key families: `host:<id>:cache`, `deploy:<host>:<service>`,
`db:<host>:<name>`, `browser:<desktop>`, `workspace:<host>:<id>`, `branch:<host>:<repo>:<name>`. An effect reserves
only resources its effect row names. `receiverVerdict(status, key, fence)` is the verdict a fence-checking receiver
must reproduce (`current`, `stale`, `unknown`). **No receiver in this plugin checks it**: every reservation is
`enforcement: "advisory"`. Human, native or full-access actors can bypass it. Reservation and maintenance rows cited in
a policy, approval or model vector are refused by `checkPolicy` (accounting, never authority).

## Cleanup boundaries (`planCleanup`)

Every job needs at least one `path-prefix` selector: an absolute directory below a root, without empty, `.` or `..`
segments (`CleanupSelectors`). A candidate is selected only when its absolute path lies **strictly below** a path
selector, compared by whole segment (so `/cachet` is outside `/cache`, and the selector root itself is never an item).
A `cache-prefix` selector only narrows path selectors: when present, the candidate's cache label must match it by whole
segments (`npm` covers `npm/_cacache`, never `npmrc`) and contain no `.`/`..`; a label never admits a path outside the
path selectors. Retained worktrees and volumes are excluded by **containment**: a candidate that equals, contains or
lies under any retained path is excluded. Retained paths are the executor's worktree paths, path-shaped `retained`
entries, and the paths of candidates tagged with a retained workspace/volume identity. A candidate listed twice is one
item. Selection inside a path selector is compared exactly (it can only narrow). Retained paths are canonicalized
(`\` read as `/`, duplicate separators and `.` segments dropped) and compared case-insensitively, so a Windows worktree
reported as `C:\Users\…` still protects `c:/users/…`; over-excluding is safe. A retained path that is relative or has a
`..` segment cannot be canonicalized without the filesystem, so the whole pass defers with nothing dispatched
(`RetainedPathError`). Symlink and junction aliases are invisible to string comparison: resolving every path (realpath)
is an **S11 executor-approval requirement**, stated on the executor contract. `retainedWorkspaces()` (`server/archive-inventory.ts`) supplies every workspace an unarchived persisted
session names **and the directory it works in**, through the same paginated history read as `archiveChildren`. It throws
rather than return a partial set, including when an unarchived session has no workspace identity or working directory
(`workspaceId` is optional in the protocol). An incomplete listing defers the pass with nothing
dispatched. Unknown-owner candidates are excluded into durable triage (a count and one `triage` incident), never
dumped to General. S10 adds no deletion authority: there is no executor, and a reservation grants nothing.

## Timer disposition inventory (`timerInventory`, `readTimerInventory`)

Read-only. Script watches (schedule, enabled from `disabledWatches`, invalid), managed watches, native schedules and
heartbeats when a listing is supplied, and the plugin's three internal clocks. Dispositions: `legacy-retained`,
`disabled-retained`, `invalid-retained`, `held-unknown-owner` (a native schedule/heartbeat whose target is not the
configured first mate), `observed-by-job`, `retired-by-job`, `plugin-internal`. Problems name a duplicate cleaner (an
active advisory job beside its enabled legacy timer) and a linked timer missing from a complete inventory. Hashes of
configuration, timers and coverage give A17.preserve's before/after comparison. `nativeSchedules()` reads protocol
`schedule/list` on the plugin session channel and reports any failure as `complete: false`. It is unwired and was
**not exercised against a live daemon**: only its parse and fail-closed result are qualified here.

## Journal budget

Every S10 write declares a step (`stepRoom`, `server/supervision-resources.ts`):

| Step | Writes | Allowed |
|---|---|---|
| admission | new occurrence, new reservation or grant, job definition or activation | below **160** (`MAINTENANCE_ADMISSION_CEILING`) |
| relabel | a waiting pass moving between pending, offline and deferred | below 160; past it nothing is written (the row keeps its last state) |
| closure | starting a pass that already holds a granted reservation, dispatching under it, an inventory deferral, an observed outcome, lease expiry or renewal | below **192**, never into the reconciliation tail |
| settlement | results of dispatched items, uncertain conversion, release, reconciliation, acknowledgement, stop | always, within the store's 256 and S07's release reservation |

Between 160 and 192, S10 writes only finish work already admitted: each pass restart needs its reservation already
held and is capped by `maxPasses`; observe mode writes at most once per state per host and occurrence, whatever the
reported digest. Past 192 only settlement continues. Lease lengths on reserve, promote and renew share one bound
(1 s to 7 days), so a bound owner cannot cycle renew and expire. From 160, `maintenanceSummary` reports "Maintenance
observation budget exhausted" and reads as a lower bound, because waiting states and new outages are no longer written
(as S08 does at 128). The store's own 256 ceiling and S07's
release reservation still apply. S08 stops at 128 and S09 at 192 in the same journal, and all of them advance one
sequence: S10's real budget is 160 minus whatever else was written. A daily three-host advisory job costs about ten
transactions a day, so this journal covers a short trial only. Long-lived activation needs the planned measured
storage work, as S08 and S09 recorded.

`drive()` and `tick()` isolate faults: a refused job open or a refused host (the ceiling, a store refusal) is reported
as `refused` and the remaining jobs, hosts and finishable passes still run.

## Limits

- **Advisory, cooperative only.** Actor kinds and bindings come from callers, as everywhere in S01–S09. No receiver
  enforces fences; strong mode (S11) needs every writer or the receiver to check them.
- **More than one process.** `runHost` guards concurrent passes per process (`active`) and the journal allows one running
  pass per job and host. A second process that finds a pass running marks its dispatched items uncertain, or (with
  nothing dispatched) supersedes it on the next day; the original process then rereads its reservation under the journal
  lock before dispatching and dispatches nothing.
- **Inventory reads.** `nativeSchedules()` and `retainedWorkspaces()` use the plugin session channel's protocol
  messages, not a public SDK API, and were not run against a live daemon.
- **No executor or wiring.** No timer calls `drive`, no RPC exposes the summary, and Bearings is unchanged.
- **Item batches.** At most 64 new items are dispatched per pass and 256 per host pass in total.
- **Lookback.** The missed-day walk stops after 400 days; the count is then a lower bound.

## Activation material (gated, not performed)

Preconditions: R10 done; D5's live definition/routing change approved under the existing watch-configuration
authority; a qualified writable coordinator store; and, for advisory mode, a qualified receiver (S11). Until then only
observe mode is meaningful.

1. Take `readTimerInventory` with a complete `nativeSchedules()` listing and record its hashes.
2. Define one job per domain in its maintenance scope, `mode: "observe"`, linked to its legacy timer with disposition
   `retained` (the 03:15 storage timer keeps its schedule and full host set, Light included). Activate it.
3. Drive `tick` and record the legacy timer's reported runs with `observe`. Compare inventory hashes: unchanged.
4. Advisory mode only after the legacy timer is retired through its known owner, recorded with evidence, and a
   qualified executor/receiver exists. Never create a replacement heartbeat while ownership is unknown.

**Rollback:** `setState(..., "stopped")`. No new occurrences; running and unknown reservations, per-host receipts,
items and incidents are retained. Restarting an old timer is not part of rollback and needs its own reconciliation.

## Overlap

S10 adds five `SupervisionRowKind`/mutation entries, one validator pair in `apply`, the optional `maintenance`
projection, one `checkPolicy` guard, `retainedWorkspaces`/`nativeSchedules` beside `archiveChildren` (which now shares
the paginated history reader, unchanged in behaviour), `WatchConfigStore.fingerprint`, and `readTimerInventory` plus an
unwired `timerInventory()` on the watch service. It changes no reducer, workflow command, Needs-you, mate, watch run,
migration, gate or source adapter behaviour.

## R10 corrections

R10 (`data/fm-ss-r10/report.md`, reviewed head `32b8e2ac`) did not accept the slice. Each finding's disposition:

- **B1 (blocking): the cleanup boundary bounds deletion.** Retained paths exclude by containment, including a candidate
  that contains a retained worktree and the selector root itself. Path selectors are required and validated;
  `cache-prefix` matches whole segments, refuses dot segments and only narrows path selectors. Candidates are deduped by
  item key. `retainedWorkspaces()` returns workspace IDs and worktree paths and fails closed on a session missing
  either. The reviewer's P3 and P10 probes are regression tests.
- **B2 (blocking): `withdrawn` needs real terminal evidence.** An effect withdraws only once `cancelled`; a host pass
  only when it is not running and dispatched nothing. `runHost` rereads its reservation and pass under the journal lock
  before dispatching. The reviewer's P4 (build granted beside a running prune) and P5 probes are regression tests, plus
  a two-process case where the reservation is released under a paused pass.
- **N1:** per-job and per-host fault isolation in `tick`/`drive`; the ceiling test now asserts the earlier pass finishes.
- **N2:** stopping a job supersedes passes with nothing unsettled and releases their reservations.
- **N3:** the step table above; observe mode writes once per state.
- **N4:** `expire` takes no time argument and needs the captain/mate or the holder scope's bound owner.
- **N5:** a crash-stranded running pass with nothing dispatched is superseded by that day's run.
- **N6:** a failed pass can no longer hold unsettled items; store-level negative tests cover dispatched items outside a
  running pass, the pass-budget row check and one open incident per job/host/kind.
- D5 semantics are unchanged (the reviewer confirmed them). The N7 notes stand as recorded: an advisory job declared
  without a legacy-timer link beside an unlinked cleaner in the same domain is not detected; that guard is needed
  before advisory activation, alongside the live-daemon reader checks.
