## Conversation behavior

The existing FirstMate chat switches to the new discussion view only when the read RPC advertises its separate UI
gate. Production wiring advertises both UI and execution **false**. The shared stream defaults to FirstMate.
Leading `@mate` selects exactly one scope; leading `#project` supplies project context without changing the recipient.
Both may be combined in either order. Dedicated discussion selection supplies an explicit default recipient. Later
mentions, quoted text, code and Markdown headings remain message text. Unknown/ambiguous names, multiple recipients,
missing scopes and changed bindings refuse; there is no broadcast or substitution of General.

Addresses resolve against stored scope UUIDs, exact plan IDs and unambiguous recorded project aliases. Conflicting
aliases remain ambiguous; the scope picker provides exact identities. `Project Mate` is not introduced as terminology.
The recipient and project context are visible before Send. Each submitted message captures home, scope/version,
epoch, agent, conversation and reply reference. The daemon resolves the authored address again and checks that
captured target at reservation; S04 rechecks its binding at dispatch. Tags add no execution authority.
Body whitespace is normalized consistently with the RPC while interior newlines remain intact; the original
addressed input remains in the request fingerprint. Invalid size/reference input is refused locally with the draft
intact. Remote bindings remain read-only before any local lookup or reservation, and native links explicitly select
the originating server when its identity is available.

Conversation/draft keys include the absolute home identity and scope; draft/send state also includes the host.
Selection, text and reply references survive component remount and bundle reevaluation in the app's global state,
as the existing drafts do. They are device-local, not a new cross-device draft-sync service. Conversation records
are shared home files using the existing confined/versioned item-thread mechanism. The thread is reserved before a
native call. Exact accepted replay returns the original record, even after ownership transfer. Lost replies retain
the original request and uncertainty; another scope remains independent. A provable pre-reservation refusal restores
the captured draft. A message typed while a send is pending is retained separately from a refused earlier message.

Shared replies come only from each message's dedicated reply file. Recipient, captured agent and reply ID are shown;
an absent reply is explicitly awaiting reply. Full native histories are not fetched, merged, or forwarded into other
model contexts. The existing host `navigation.openAgent` opens the exact same session for dedicated-tab continuity.
Reply files and actor labels are same-user behavioral attribution, not authenticated channels or fencing.

The plugin owns this composer and uses existing `defineRpc`/`server.handle`/`useRpc` and host navigation. The installed
0.11 SDK has no general native-composer interception hook that can safely reroute an ordinary prompt. No workaround,
native tab manager or embedded browser is added. Ordinary prompts in native agent tabs retain their native recipient;
shared `@`/`#` routing belongs to the plugin's shared composer. A future request to intercept every native prompt would
need a supported pre-submit contract with explicit recipient, text, attachments, correlation ID, cancellation and
exact accepted/uncertain receipt semantics; composer pills/attachments and timeline transformations do not supply it.

## Lazy sessions and authority

First explicit Send displays activation before reserving a previously uncreated plan/project discussion session.
It uses S04's reserved workspace/create/opening effects, exact identities, verified binding and cumulative limits.
There is no eager session on view/restoration, no automatic replacement, no fresh-ID fallback, and no second send
after an unknown result. Existing General launch/adoption controls remain explicit. Maintenance discussion has no
qualified adapter and remains read-only.

New discussion-created bindings durably carry `purpose: discussion`. S03 refuses worker starts from them; S04 refuses
worker effects again at dispatch. S04 goal reconciliation does not turn their creation into a work pass. A separate
checked work activation is required; this slice exposes no promotion shortcut. Historical bindings without this
additive field retain S04 behavior. Manual replacement preserves a discussion-only purpose. The technical existing
supervisor role label remains a home guest and is never a global-mate role.

Created sessions persist with their context while dormant. Activity uses optional exact owner observations from the
existing lifecycle, expires to unknown, and is invalidated on turn reservation. Send acceptance never means awake or
finished. Observation writes are excluded from semantic continuation inputs, with CAS pinned to the observed binding.
Project turns retain their own relevant mailbox; unchanged state causes no model pass. Project plan-command
outboxes have no qualified handler yet and explicitly hold instead of causing a summary or General fallback. This
slice's captain discussion is a direct reserved input to that session. It does not invent S02 project worker/watch
event adapters: S02's accepted native worker observations still require exact registered attempt/task ownership and
route directly to that owner. Broader relevant watch/judgment ingress remains its separately qualified source adapter,
not an automatic forwarding of every plan result to project or General.

## Status and Needs you

`firstmate.scope.read` reads only stored state. It does not call a receiver, initialize a store, repair a journal,
create a session or wait behind a native send. It reuses S04 `goalStatus`: goal/project owner, unfinished outcome,
next action/wait, tracked workers, pending/uncertain effects and evidence age. Project rollups include nested plan
workers without recounting them. Capacity failures, holds, missing observations and source coverage are visible.
The timestamp describes the stored snapshot; unknown source coverage is not a claim of a complete native fleet.
An accepted intermediate result with zero workers stays needs-planning. Paused goals and uncertain attempts remain
accounted for. Status has on-demand refresh, with no new scope timer or watcher.

The existing `withScopedNeedsYou` projection supplies the same decision IDs, readiness, holds and lower-bound counts.
The drawer reuses `DecisionTask`; its adapter never writes backlog-ledger requests. Source/subject/revision and the
S03 command read set are displayed and submitted through `firstmate.scope.answer`, which calls the existing checked
answer transaction. Answer/outbox commit remains atomic. Logical captain answers survive owner transfer; the old epoch
cannot handle them. No approval, policy exception, head/check evidence or model authority is invented by the UI. S03
may refuse requirements not met by the displayed context. Existing native permission answers remain in their qualified
native conversation rather than being silently mapped to a different request.

The answer is disabled after submission, including if its combined reread fails. Poll/response merging keeps the two
independent journal versions monotonic and does not resurrect an answered decision. Scoped read failures leave legacy
decisions available and label totals incomplete. Plan/decision links open the existing Home discussion destination;
viewing, filtering, restoring and navigation grant no approval.

## Activation and rollback boundary

`registerScopeRpcs` defaults both gates off; production `index.server.ts` explicitly supplies false/false and no
discussion service, commands, writable store, gateway or receiver. A separately approved qualification would have to
inject those existing S03/S04 components, a server-owned profile/limits source and a qualified native adapter, while
preserving current coordinator, capability, policy, C2 and uncertainty holds. An arbitrary environment variable or RPC
cannot enable it. `scope.activate` is deliberately a non-mutating refusal directing callers to explicit Send.

D3's lazy/persistent arrangement is reflected here; the separately metered 7-session/18-turn trial and installation,
live routing, execution, maintenance and release authority remain separate. UI enablement alone permits only reading.
Rollback hides controls while preserving drafts, thread files, decisions, purpose/ownership, attempts and spent budget.
No journal/history migration or cleanup is performed. No strong authentication/fencing or provider latency guarantee
is claimed. Independent R05 acceptance is still required before landing.

## Verification

R05 recovery corrections retain scoped-mode intent in the existing device-local draft store, keyed by the same
host/source-home tuple as the scope query. Query-cache removal and chat remount cannot expose the legacy General
composer after scoped mode was observed. An unavailable restored view offers an explicit read-only refresh; recovery
reuses its original scope selection and addressed draft, including when the daemon canonicalizes the home spelling.

The answer RPC now distinguishes a proven refusal from uncertainty. It reports `refused` only for a checked
`SupervisionError` followed by a current, same-home store read with no accepted command for the exact submission ID.
Publication holds, unreadable state, transport errors and errors after acceptance retain uncertainty and the original
submission. A refused answer keeps its notes/option, refreshes the combined context and permits a new explicit
submission. If that read fails, notes remain editable and submission waits for an explicit successful refresh.
Neither an exception nor a still-pending decision alone proves non-acceptance. No automatic answer resend is added.

The actual-component render includes R05-F1/F2 in all four theme/width cases, plus uncertain-answer refresh/remount
controls. The real S03 policy-refusal reproduction and interrupted-publication/exact-replay controls are retained in
`server/scope-discussion.test.ts`. `S05-R05-verification.json` pins this correction's source and executed receipts;
the earlier `S05-verification.json` remains historical evidence for its reviewed source, not a current-head claim.

`server/scope-discussion.test.ts` drives actual S01/S03/S04 components with isolated homes and synthetic receivers.
It covers resource-free reads, General/project/plan routing, first activation and reuse, stale/unknown targets,
reply correlation, exact replay after a lost send, changed-body refusal, cross-scope independence and transfer-safe
decision answers. `server/scope-projection.test.ts` exercises intermediate success/zero-worker, two ready tasks,
nested worker counts and capacity failure. Parser, draft/send-gate and independent-version count tests cover the
client seams. Existing S04 continuation/lifecycle tests retain lost callback, stale transfer, unchanged retry, pause
and two-independent-ready-task controls; they are reused rather than replaced by another engine or qualification job.

`node docs/scoped-supervision/s05-ui/render.mjs` mounts the real chat, scope picker and decision controls against
synthetic host APIs in light/dark themes at 1440x1000 and 390x844. It checks captured-target send during scope switch,
draft remount, unknown addresses, explicit activation copy, resource-free views with General absent, native session
links and disabled confirmed answers when reread fails. Evidence stays in ignored `.local/s05-ui/`; CI retains it as
artifacts. These are phone-browser fixtures, not installed device/provider acceptance. `s05-compile.cjs` uses the
installed desktop compiler read-only and Hermes on both this source and pinned S04; outputs remain under `.local/`.
The delivered S05 verification manifest pins source/test bytes and executed receipts. Exact-head CI is separate.
