RPC registration, request consumer, timer, model call, send, resource creation, release executor,
installation, live activation or legacy migration. The selected scope must be registered in an
isolated store before a fixture explicitly enables `SupervisionCommands`. Ordinary plugin paths
continue using their existing backend and answer delivery.

## Admission and history

`server/supervision-policy.ts` accepts explicitly reviewed source records and a closed pilot
vocabulary: `plan.start`, `plan.review`, `plan.stop`, `plan.record`, `decision.answer`, `model.use`.
Every rule names exact scope, plan, project ID/name and normalized host selectors. A grant is needed
for every project; applicable constraints intersect, and a deny holds the affected operation.
Sources retain home-relative file path, exact line range, file/excerpt hashes, provenance, version
and explicit supersession. Files are confined and bounded, and are checked again at admission.
Worker/agent and memory/quoted-text proposals do not enter the reviewed acceptance adapter.

New commands check home, scope version, active binding/epoch, logical owner, backend, current plan
hash/revision/subject, exact dependency plan/outcome/hash/revision/attempt bindings, pinned brief,
policy/evidence versions, model provider/mode/thinking profile constraints and any required operation
approval. Evidence binds exact head/artifact, check result and distinct independent reviewers;
duplicate observations from one reviewer do not increase the independent count. Conditional model
fallback requires recorded observed unresponsiveness or quota refusal; unknown availability grants
nothing. This slice records supplied evidence; source observation/adapters belong to S08.

Operation approvals bind operation, scope/plan/revision/subject, head/artifact, both launch and model
policy vectors, model profile, evidence vector, provenance and optional expiry. Plan review and
operation approval remain distinct; neither permits merge/deploy/install/discard/publish. Unchanged
valid grants survive session replacement without another approval request.

`SupervisionStore.transactCommand` checks the accepted request index **before** present-day admission.
An exact accepted request returns its original result and transaction receipt even after policy,
source or binding changes, or with command writes disabled. Changed content/provenance under that ID
refuses. Preparation, version checks, changes, accepted-result index and logical-owner outbox publish
under the same existing coordinator/serialization boundary. The transaction wire format is retained;
typed outbox rows live in its mutation batch, not a second queue or file publication.
Bookkeeping acknowledgements produce no additional notification, avoiding an acknowledgement loop.

The adapter uses `replaySupervisionWorkflow` and the existing reducer for definitions, one-step
automatic work, attempts, cumulative spend, review edits, history, invalidation and completion.
`checkNewCaptainAction` is the shared new-append guard; historical replay never calls it.
Read commands use the existing reader. `release`, `replace`, `retire` and `notified` refuse in this
new seam until their checked lifecycle/migration adapters exist. Their legacy semantics are unchanged.
This conservative refusal is deliberate: no unqualified assertion that a start is uncreated.

## Stops, source changes and answers

A stopped plan commits its workflow hold, operation hold, cancellation of still-reserved effects
and owner notification intent together. Dispatching/accepted/uncertain effects and their resource
and spend records remain; there is no claim of retroactive cancellation. S04 owns safe-stop effects.
Explicit source/rule changes commit narrow operation holds in the source-change transaction, before
anything can notify a model. Releasing one requires a separate exact-version reviewed receipt via
`acceptPolicyInventory(..., { reviewedHolds })`. Neither viewing nor approving a plan releases it.
Conflicting rules still refuse after a hold is released. Raw source drift refuses admission until
reviewed; it does not trigger a model wake or an automatic grant import.

`answerScopedDecision` addresses a durable decision ID, revision and subject. It commits the existing
workflow answer, accepted answer/provenance and one outbox row together. Two devices cannot both
answer the same question. Changed questions refuse and leave the caller's draft untouched.
Captain UI answers address the **logical scope**, so transfer preparation or an old displayed
session epoch does not discard an otherwise current answer. They still check decision/plan/policy
vectors. Mate-recorded chat actions retain the bound mate identity, quoted source and epoch checks.

The outbox names a logical scope, never a cached recipient agent. `pending()` only reads its current
binding; hold/transfer exposes no delivery target. The current owner acknowledges with its epoch,
outbox ID and a `command:<request UUID>` reference to its later committed same-plan result. Arbitrary
or transport-only references and old owners refuse. Lost delivery does not erase the answer
or mark it handled; a later informational offer can retain the same ID. S02/S06 own offers and
delivery activation. Transport acceptance is never inferred to be a handled result.

`withScopedNeedsYou` is a read-only composition seam. It exposes scoped decisions, owner epoch,
pending-answer deliveries, operation holds, sequence and completeness beside legacy rows. Not-yet-due
decisions never enter action counts. Holds count once per affected plan; repeated composition does
not accumulate counts. No service currently invokes this seam automatically. S05/S06 must integrate
the separate scoped answer class rather than routing these rows through `askMate`.

## D4 selection and activation handoff

The reviewed input is S00 corrections inventory
`data/fm-ss-s00-corrections/contracts/authority-inventory-v1.json`, in manifest
`343444b790d0f8ad17b6458f804b65f564f083b6825536ef72d4f04034a7b135`.
Its `implementation`/`latest-approval` records bound implementation/test scope and direct-state,
lazy-session, no-summary-cascade constraints. `model-exception` is conditional; completed reviews
remain retained. FIFO within equal priority and no automatic quota borrowing remain D4 design
constraints for the later scheduler, not an executor introduced here. Unknown usage remains unknown.

The `FirstMate-merge`, `head-evidence` and `FirstMate-install` inventory entries remain source-bound
legacy authority. This slice neither transfers the existing mate's merge authority nor widens the
earlier exact-build installation exception. Other projects' grants are excluded. Broader inventory
and project agreements belong to S09. No terminology migration is included.

Before any separately authorized activation, the integrating slice must:

1. Retain the pinned accepted dependency/report and D4 selection; recheck the source files/ranges
   against the inventory. A hash mismatch is review work, not permission to refresh a grant silently.
2. Register a new scoped plan/backend/task set with exact project aliases and independent owner
   binding. Materialize only the selected pilot operations as reviewed `PolicySource`/`PolicyRule`
   records; keep release/install records outside the executable vocabulary.
3. Supply the qualified caller/provenance adapter and supported lifecycle/evidence capability set.
   Enable both compatible legacy/scoped writer and delivery partition gates before routing a scope.
   Current legacy request files are not a new scoped transport.
4. Qualify S04/S05/S06 integration and the remaining D1-D3 gates, including budgets and source/owner
   routing. S07 separately owns legacy answer/note cutover; M1 requires **A07.scoped**, not A07.legacy.
5. Roll back by holding admissions while retaining policy sources, accepted answers/results, outboxes,
   spent budget and uncertain effects. Do not remove rows, reset IDs or reinstall an incompatible writer.

These steps are review material, not live authorization or an executable activation script.

## Verification and limits

`server/supervision-commands.test.ts` uses temporary homes, the actual store/reducer/service seams and
synthetic process identities. It covers A01/A03/A05/A07.scoped/A11/A15 within this slice, including
head/check drift, accepted replay, both stop/admission orderings, two-device answers, transfer,
publication interruption/recovery, model/profile and conditional fallback, exact ownership,
independent project progress, automatic one-run reuse, UI/chat provenance and read-only counts.
The retained [validation receipt](s03-validation.json) records final commands, results and source/test
digests. Existing storage, workflow, Needs-you and launch tests remain applicable; CI retains its
Windows/Ubuntu full-suite and render artifacts. No client rendering was changed by this slice.

This is a cooperative gateway seam. Same-user file actor assertions are not authenticated identity;
full-access peers can bypass it. Source-file inspection does not lock arbitrary Markdown editors.
Mediated source changes share the journal boundary; a raw edit after a checked read is outside that
boundary. There is no native/receiver fencing, automatic takeover, strong isolation or live-runtime
qualification. No external release or model call is made under the journal lock. Existing process-
crash guarantees and coordinated-local-metadata-loss limits from S01 remain.
