# Projects

Admitted projects are context for Supervisors and plans: identity, folder, allocation, sponsors, conflicts and memory. A project needs no session of its own. This guide is also written to `data/project-mates.md`, its old name, for sessions that were told that path.

Available while the captain's saved Supervisors setting is on (until one is saved, the daemon's old environment switches stand in). Changes apply while services are running. When Supervisors are off, new work refuses and saved records remain available for inspection. Viewing creates no sessions. The captain may add a project's Supervisor from Supervisors' **Add project Supervisor**, and the current first mate may provision the same Supervisor through `tools/supervise.mjs` (below), after the project is admitted with its allocation recorded. Either way the model, permissions, cumulative session/turn limits and opening are the reviewed ones, caps stay within the admitted allocation, and the record names who provisioned it.

If project records are held after an interruption, the app's **Recover project records** action validates the inspected journal tip and repairs only a valid derived checkpoint or complete pending publication. It creates no workspace, agent or turn, and refuses missing or divergent authority history. Then continue the recorded provisioning input through the route that started it: Supervisors' **Resume ‹project› Supervisor setup** for an app-started request, or the same supervise request for a first-mate one, including after a restart. An uncertain opening is never resent. The app's **Stop this setup** cancels only undispatched operations and retains the original identity, spent budget and uncertain outcomes; it never creates a replacement. Recovery itself stays an explicit app convention, not a helper or first-mate action.

Read the registry census and project-plan associations with `node tools/projects.mjs read`. Each active registry row is accounted for, including unavailable, ambiguous or remote rows held for explicit mapping. Local identities derive from the canonical directory and home, never a guessed name. Legacy plan membership is pending migration; project oversight does not transfer its writer or callbacks.

A project's bound Supervisor reads and acknowledges its own checked inputs through `node tools/scope.mjs read|inbox|outbox|project-result --file data/<request>.json --request-id <uuid>` (see `data/supervisors.md`). These existing transports retain the exact scope/epoch and request bytes. They grant no plan execution or Attach. General keeps using the project administration transport below.

The current first mate may record reviewed captain instructions through `node tools/projects.mjs command --file data/<command>.json --request-id <uuid>`. Reuse the same UUID and bytes after a lost reply. The strict command vocabulary is `admit`, `project`, `sponsor`, `release-sponsor`, `promote`, `intake`, `resolve-conflict`, `resolve-dependencies`, `memory-propose`, `memory-decide`, and read-only `memory-read`. No command here creates a worker or a Supervisor; provisioning is its own command, next. Files and actor IDs are cooperative role checks, not authentication.

To provision an admitted project's Supervisor yourself, use `node tools/supervise.mjs command --file data/<request>.json --request-id <uuid>` with `{op: "project-provision", provision: {projectId, projectVersion, profile?, limits?, opening?}}`, taken from `projects.mjs read`. Omit profile, limits and opening to use the admitted ones with the default opening. Reuse the same UUID and bytes after a lost reply; the recorded request is resumed, never duplicated, and it records you as its actor. Only the current first mate may submit it.

`admit` names the displayed registry digest, one registry name, aliases, an explicit `{agents,turns}` project allocation, `{provider,modeId,thinkingOptionId}` profile and `{supervisorSessions,supervisorTurns}` cumulative caps. Its reviewed `source` uses the S03 policy-source contract: exact home-relative path, file/excerpt SHA-256, inclusive lineStart/lineEnd, UUID/version, supersedes, and provenance `{kind:"mate-chat",id:<current-mate>,source:"project administration (same-user role convention, unverified)"}`. It grants no operation. Unknown or changed sources refuse. Read `shared/project-runtime.ts` in the installed source for exact strict shapes; do not invent fields.

`project` uses projectId, expectedVersion, state, budget and current sourceVector to stop, re-admit or change allocation. Stopping keeps spend, memory, identity and admitted effects; it cancels only affected reserved effects. `sponsor` takes planScopeId, expectedVersion, sponsorScopeId (null chooses General for cross-project work) and one `{projectId,agents,turns,priority}` claim for every project. Only an already scoped plan is eligible. Claims are all-or-none FIFO within priority, with no borrowing. Sponsorship never changes the plan execution owner.

`intake` uses the original intakeId, textDigest, one registered plan ownerScopeId, projectIds and exact scoped tasks. Repeated forwarding cannot create another owner. Factual conversation is not an intake command. Conflicts retain their General or single-project owner until a versioned choice is recorded; a choice does not execute its proposed change.

`memory-propose` takes projectId, key, expectedVersion, text and evidence. `memory-decide` takes proposalId, proposalVersion, decision (accept/reject), and memoryVersion. Compare-and-set refusal keeps the proposal. `memory-read` takes projectId and returns capped, digest-verified accepted context and pending proposal text. Home/Plans offers the same read-only review. Memory is never a grant, approval or evidence for effects.

General keeps the reviewed per-home plugin capacity and admission headroom (default: 4 slots, 1 reserved for General). Saved values override the original home's legacy environment capacity. Actual provider availability is separately unknown. Native/raw callers remain outside this cooperative accounting. Enabling controls alone creates no session or worker and performs no migration or Attach; each Supervisor is still set up one at a time, by the captain's button or your supervise tool. Existing project Supervisors may receive their checked inputs within their retained cumulative limits; a project Supervisor has no plan execution authority.

Project provisioning uses its own per-project queue. Only the short capacity check and reservation share an admission queue with scoped Attach; native IO runs outside it and never holds General's conversation lock. Current home, General ownership and project/source admission are checked again before each new external effect.
